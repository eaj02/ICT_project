## 5. 실제 낙상과 기기 충격 구분 ★ (학술 근거 정정 핵심 슬라이드)

가장 중요한 문제는 이것입니다. **실제 낙상과 단순히 기기를 던지는 상황을 어떻게 구분할 것인가?**

단순히 가속도만 보면 두 상황은 매우 비슷합니다. 실제 낙상도 큰 충격이 발생하고, 시계를 벗어 바닥에 던져도 큰 충격이 발생합니다.

**참고로 본 시스템의 가속도 임계값은 Habib et al.의 2022년 Frontiers in Public Health 리뷰 논문에서 보고된 표준값을 따랐습니다. 경고는 2 g, 낙상 후보는 3 g 입니다. 자이로스코프 임계값 200 °/s 는 Bourke와 Lyons의 2008년 Medical Engineering & Physics 논문에서 wrist 부착 환경의 표준 임계값으로 보고된 값을 따랐습니다.**

**하지만 이 임계값들만으로는 충분하지 않습니다. Kangas et al.의 2008년 Gait & Posture 연구는 wrist 위치의 낙상 감지 정확도가 75% 수준으로 waist나 head보다 낮다고 보고합니다. 즉 손목에서는 단순 임계값만으로 fall 과 일상 동작을 구분하기 어렵습니다.**

**또한 가속도와 자이로 두 신호의 시간 순서도 중요합니다. 실제 낙상은 보통 "회전(낙하 중) → 충격(바닥) → 정지" 의 순서로 신호가 나타납니다. 이 순서를 무시하고 두 신호의 최대값만 따로 보면, 손목을 책상에 부딪힌 단순 충격이나 손목을 제자리에서 비트는 회전 동작이 fall 로 잘못 분류될 수 있습니다.**

**그래서 본 시스템의 motion score 는 가속도 충격 시점을 anchor 로 잡고, 그 시점 전후의 신호를 시간적으로 연관해서 평가합니다. 구체적으로 세 가지 단계 점수가 있습니다.**

**첫째, IMPACT — 가속도 3 g 이상 충격이 한 번이라도 잡히면 0.30 점. 이게 없으면 회전이 아무리 격해도 0 점입니다. 손목 비틀기 같은 일상 동작이 false positive 가 되는 걸 막는 첫 관문입니다.**

**둘째, CO-ROTATION — 충격 시점 ±2 tick 윈도우 안에 자이로 200 °/s 이상이 같이 잡히면 0.25 점 추가. 이건 Huynh et al. 의 2015년 Journal of Sensors 논문에서 제안한 "fall window 안에서 가속도와 자이로를 동시 확인" 방식을 따른 것입니다. 충격과 회전이 같은 사건의 일부라는 증거입니다.**

**셋째, POST-INACTIVITY — 충격 이후 가속도가 0.5 g 미만으로 약 2초 이상 정지하면 0.45 점 추가. Bagalà et al. 의 2012년 PLOS ONE 논문이 정립한 four-phase fall 모델의 post-fall phase 에 해당합니다. 사람이 쓰러진 뒤 움직임이 멈춘다는 결정적 증거입니다.**

**셋을 모두 만족하면 motion score 1.0 으로 EMERGENCY_FALL. 회전 없이 충격과 정지만 잡혀도 0.75 로 EMERGENCY (옆방향 낙상 등). 충격만 잡히고 회전·정지 없으면 0.30 으로 WARNING. 회전만 격하면 0 점 NORMAL 입니다.**

여기에 wear score 와 data quality score 를 함께 봅니다.

wear score는 심박과 피부 접촉을 통해 사용자가 실제로 기기를 착용 중인지 확인합니다. data quality score는 패킷 손실과 보간 비율을 보고 데이터가 신뢰 가능한지 판단합니다.

**핵심은 이것입니다.**

**같은 3 g 이상의 충격이 발생해도, 시간 순서상 회전과 정지 패턴이 함께 잡히고 착용 신호가 유지되면 실제 낙상으로 판정합니다. 착용 신호가 사라지면 같은 충격이라도 기기 투척으로 분류합니다.**

이제 이 구조가 실제로 어떻게 동작하는지 프로토타입으로 보여드리겠습니다.

## 1. Title Slide

Hello, everyone. My name is Yoonjae Jeong, and this is my personal project: a wearable-based real-time fall detection system.

This project is not just about detecting whether a fall happened or not. The main goal is to build a prototype that can collect wearable sensor data, handle network loss and delay, recover missing data, and make real-time decisions on the server side.

There are three key ideas in this project. First, the system handles packet loss in UDP-based transmission. Second, it uses multi-modal scoring to reduce false positives. Third, it supports server-centric monitoring, where multiple users can be monitored together on one dashboard.

---

## 2. Risk of Falls

Before explaining the system, let me briefly explain why fall detection is important.

According to the World Health Organization, 28 to 35 percent of people aged 65 and older experience falls every year, and falls are among the leading causes of unintentional injury death globally.

So, detecting falls quickly is not just a technical problem. It is a real-time safety problem.

---

## 3. Difference from Apple Watch

Of course, fall detection already exists in commercial products such as the Apple Watch. However, the purpose of this project is not to replace the Apple Watch.

The Apple Watch is closer to an edge-computing model. It collects sensor data and performs the fall detection process close to the device itself.

In contrast, this project uses a cloud-centric, or server-centric, structure. The wearable device sends raw sensor data to the server, and the server collects, recovers, analyzes, and monitors the data.

So, the main focus of this project is not product-level performance comparison. Instead, the focus is to show how multiple wearable devices can be monitored in real time under network constraints.

---

## 4. System Architecture

The system is composed of three main parts.

First, Process A works as the edge or sensor node. It generates accelerometer, gyroscope, heart rate, and skin contact data. Then, it sends the raw sensor data to the server using UDP.

Second, Process B works as the server node. The server receives UDP packets, stores the data, and recovers missing values using linear interpolation when packet loss occurs. After that, it applies the fall detection logic.

Finally, the result is visualized on a Streamlit dashboard. The operator can monitor multiple users at a glance through a card-based grid interface.

One important point is that I intentionally added about 15 percent packet loss during transmission. This means the system is not tested only in a perfect network environment. It is designed to work even when some sensor data is missing.

---

## 5. How to Distinguish a Real Fall from Device Impact ★

The most important question is this: **How can the system distinguish a real fall from a simple device impact?**

If we only look at acceleration, these two cases can look very similar. A real fall creates a strong impact, but throwing a smartwatch onto the floor can also create a strong impact.

**My thresholds follow the standard values reported in a 2022 review paper by Habib et al. in Frontiers in Public Health. The warning threshold is 2 g, and the fall-candidate threshold is 3 g. The gyroscope threshold of 200 degrees per second follows Bourke and Lyons' 2008 paper in Medical Engineering and Physics, which reported this as a standard threshold for wrist-mounted devices.**

**But these thresholds alone are not enough. Kangas et al.'s 2008 paper in Gait and Posture reported that wrist-worn devices reach only about 75 percent fall-detection accuracy, which is much lower than waist or head positions. In other words, on the wrist, simple thresholding cannot reliably separate falls from daily activities.**

**The temporal order of acceleration and gyroscope signals also matters. A real fall usually shows the sequence: rotation while falling, impact on the ground, and then a quiet rest period. If we ignore this order and just compare the maximum values, a simple impact like hitting the wrist on a desk, or a pure rotation like twisting the wrist, can be wrongly classified as a fall.**

**So my system's motion score uses the acceleration impact as an anchor, and evaluates the surrounding signals in temporal context. There are three phase scores.**

**First, IMPACT — if the acceleration exceeds 3 g at least once, the score gets 0.30. If there is no impact, the score is zero, no matter how strong the rotation is. This is the first gate that prevents pure rotation actions like wrist twisting from becoming false positives.**

**Second, CO-ROTATION — if the gyroscope also exceeds 200 degrees per second within plus or minus 2 ticks of the impact, the score adds 0.25. This follows the "fall window" approach proposed by Huynh et al. in their 2015 Journal of Sensors paper, which simultaneously checks acceleration and gyroscope inside the same time window. This is evidence that the impact and rotation are part of the same event.**

**Third, POST-INACTIVITY — if the acceleration stays below 0.5 g for about 2 seconds after the impact, the score adds 0.45. This is the post-fall phase from the four-phase fall model that Bagalà et al. established in their 2012 PLOS ONE paper. It is the decisive evidence that the user has fallen and stopped moving.**

**If all three are satisfied, the motion score reaches 1.0 and the system classifies the event as EMERGENCY_FALL. Even without rotation, an impact followed by inactivity gives 0.75, which is still EMERGENCY (for example a lateral fall with little rotation). An impact alone with no rotation or rest gives only 0.30, which becomes WARNING. Pure rotation without impact gives zero, NORMAL.**

On top of motion score, the system also uses wear score and data quality score.

The wear score checks whether heart rate and skin contact signals are still detected. The data quality score checks packet loss and interpolation ratio.

**The key idea is this.**

**Even if the same impact above 3 g occurs, the event becomes a real fall only when the temporal order of rotation and post-impact rest is also satisfied and the wear signal is maintained. If the wear signal disappears, the same impact is classified as device-thrown instead.**

## 8. Real Fall Scenario

Now, I will apply the real fall scenario.

**[Demo: Apply Real Fall Scenario]**

As you can see, the acceleration suddenly spikes **above the 3 g threshold, reaching about 4 to 5 g, and the gyroscope also spikes to around 300 degrees per second**. Right after the impact, the acceleration drops to nearly zero and stays there for about two seconds. The same pattern is reported in public fall datasets such as SisFall and MobiFall.

At the same time, heart rate and skin contact are still detected. So, the system understands that the user is still wearing the device.

When all three conditions — strong impact, post-impact rest, and wear maintained — are satisfied, the motion score reaches 1.0 and the wear score also reaches 1.0. The final decision becomes **EMERGENCY_FALL**.

One important point is that the final decision does not immediately return to NORMAL, even if the sensor values become stable again. This is because of the event latch mechanism. If a real fall happens and the user loses consciousness, the system should not clear the emergency state too quickly. If the user is okay, they can press the I'm OK button to clear the emergency state.

## 9. Device Thrown Scenario

Now, I will show the device-thrown scenario for comparison.

**[Demo: Click I'm OK, then apply Device Thrown Scenario]**

In this case, the acceleration also spikes strongly, **going well above 3 g and reaching about 4 to 6 g**, just like a real fall. A simple threshold-based system might incorrectly classify this as a fall. In fact, the threshold-based baseline I cited — Tang et al. 2024 — reports a specificity of only 85 percent for exactly this reason.

However, in this scenario, the heart rate signal disappears, and the skin contact signal is also lost. So, the wear score drops below 0.3. As a result, even though the same strong impact is detected, the system does not classify this as a real fall. Instead, it classifies the event as **DEVICE_THROWN_OR_DROPPED**.

This shows the main idea of the system. The system does not rely only on impact. It considers the motion pattern, whether the device is still being worn, and whether the data is reliable.

## Closing (Optional)

To summarize, this system demonstrates three things.

First, even under about 15 percent packet loss, linear interpolation enables real-time decision-making.

Second, the wrist position limitation — the 75 percent accuracy bound reported by Kangas et al. — is mitigated by multi-modal scoring, which reduces the false positive problem of simple threshold systems.

Third, a single server can independently process wearable data from multiple users in a server-centric architecture.
